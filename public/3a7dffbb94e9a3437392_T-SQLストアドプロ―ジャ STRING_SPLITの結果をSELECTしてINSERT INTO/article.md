# はじめに
JavaのMybatisやC#のEFCoreのデータアクセスモデルでINSERTを数1000回以上ループさせて処理させますと完走時間が現実的でなくなります。そのような場合、それぞれのモデルの生SQL実行機能でストアドプロシージャで処理する際に、登録したい項目にランダム値を含むような場合はどうしてもその項目の値全体をアプリケーションからSQLServerに伝送する必要があります。

本記事は1000万件くらいのランダム値をCSVとしてSQLServerに伝送して、T-SQLストアドプロ―ジャ内でSTRING_SPLITの結果をSELECTしてINSERT INTOする事例です。

https://learn.microsoft.com/ja-jp/sql/t-sql/functions/string-split-transact-sql?view=sql-server-ver17

# 適応対象 
Sql Server 2016 (13.x) 以降

# STRING_SPLITの基本構文
SELECTにはvalueと書くことがお約束です。SQLServerのバージョンがいけていてもSSMSのバージョンが低いとvalueが怒られますが気にしないで実行すると完走します。

```
SELECT value FROM STRING_SPLIT('a,b,c', ',');
```
# STRING_SPLITを使ったINSERT INTO文


```
INSERT INTO table_name (
列１
列２,
列３,
・
・
・
)
SELECT 
@param1,
value,
@param2,
・
・
・
FROM STRING_SPLIT(@valuesList, ',');
```

@param1,@param2はストアドプロシージャのパラメータで、数100万件INSERTするtable_nameテーブルに対して同一値となります。

@valuesListはCSVとして登録項目をカンマ区切りなどですべて含んだ文字列です。パラメータ宣言文ではVARCHAR(MAX)としておくと安全です。valueに@valuesListの値が１件づつ入ってきますので、それを挿入したい項目位置に記述します。

計算で展開できるような場合はCSVで渡そうとせず、計算用のパラメータを渡してストアドプロシージャのINSERT INTO文中で計算させるようにすると、ストアドパラメータに転送するデータ量を削減できます。

valueの値に固定値部分を含み、その他がランダム値または欠番を含む一部連番値のような場合、アプリケーション側でCSVを作成する際に固定値部分を除去して項目の文字数を減らした方がよいでしょう。固定値部分は１つのパラメータとして渡してINSERT INTO SELECT文の中でCONCATして復元します。

# １回で転送するCSVの項目数
1000万件のINSERTとなると、CSVの文字列上限やアプリケーションサーバーからDBサーバーへの転送処理も問題になってきますので、現実には分割して処理することになります。

筆者の環境では10000件づつ処理する場合と5000件づつ処理する場合とで検証してみました。

1000万件を処理するためには10000件づつの場合は1000回反復、5000件づつにいたっては2000回の反復となるため、前者の方がトータルでははやいかなと想定しておりましたが、筆者の環境では後者のがはやいようでした。

# 性能（参考情報）

INSERT対象のテーブルの列数やサーバーの性能にも依存して結果は変動しますが、筆者の環境で1000万件はC#のEFモデルのaddによるループ処理では１時間たっても終わらなかったのに対して8分弱で完了するようになりました。（5000件づつ2000回の反復）

100万件の場合は50秒強で終わりましたので、だいたいリニアに処理時間が増加していると考えらます。

# おわりに
ユーザーが見ている前で処理しなければならない場合、完了時間が8分というのはなかなか厳しいですが、数100万件ならばなんとか実用的な構成と言えます。1000万件を１分以内で終わらせるにはINSERT対象のテーブルをオンメモリにするとしか思いつきませんが、未検証です。
